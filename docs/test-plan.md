# Тест-план

**Проект:** "Общее дело" - веб-платформа гражданской науки **Тестировщик:** Орловский Андрей, **Версия:** 1.0,
**Дата:** 06.05.2026 **Объект:** сборка от 05.05.2026, четвёртый спринт фронтенда (учебный командный проект МАИ)

## 1. Цель

Подтвердить пользовательский сценарий "учёный создаёт проект -> формулирует задание -> волонтёр присоединяется
-> присылает наблюдение с фото -> учёный модерирует" и выявить дефекты, мешающие эксплуатации, прежде всего в
**авторизации** и **целостности данных**. Цель - понять, что безопасно выкатывать, а не "пройти все тесты".

## 2. Объём

**В скоуп:** регистрация, авторизация и ролевая модель `volunteer` / `scientist` / `admin` с доступом к чужим
ресурсам; проекты, задания, наблюдения, комментарии и участие - создание, просмотр, редактирование, удаление,
права владельца; файлы - загрузка, лимиты, типы, скачивание; API - контракт, коды ответов, схема ошибок, CORS,
лимиты payload; интерфейс - адаптивность, валидация форм, состояния загрузки и ошибки, доступность;
персистентность - согласованность данных в трёх изолированных БД после операций через API.

**Вне скоупа:** нагрузочное и стресс-тестирование, Safari и Firefox, аудит зависимостей и пентест, реальные
устройства и биометрия - только эмуляция. Первые два - ограничения среды, перечислены как риски в разделе 7.

## 3. Окружение и данные

ОС - Windows 11 или Ubuntu 22.04. Frontend - Next.js 16 на `:3000`. Gateway - Actix Web на `:8080`, единственная
точка входа; микросервисы user `:8081`, project `:8082`, observation `:8083`. БД - PostgreSQL 16: `users_db`,
`projects_db`, `observations_db` на `5433`, `5434`, `5435`. Redis 7 на `6379`, MinIO на `9000`. Развёртывание -
`docker compose`, инструкция и seed-данные в [stand/README.md](../stand/README.md).

Тестовые данные: учётные записи `volunteer`, `scientist`, `admin` из seed-скрипта; проект с заданием, где в
требованиях включены флаги "требуется фото" и "требуется место" - самое интересное место для условной валидации;
наблюдения в состояниях `pending`, `approved`, `rejected`; границы 0, 5, 6, 71, 72, 73 символа для пароля и
255/256 для текстовых полей.

## 4. Стратегия

Стратегия выведена из того, где в объекте реально ломается: изолированные БД микросервисов и клиентский слой,
который сам реализует "логику доступа", дают три класса дефектов.

1. **Обход авторизации.** Правила публичности заданы префиксами, поэтому "публичным" может
  стать всё дерево эндпоинтов. Ловим таблицей прав "роль x эндпоинт x принадлежность ресурса": прогон с удалённым,
  подделанным и чужим токеном.
2. **Расхождение слоёв.** Клиент и сервер могут иметь разные представления о методах, статусах
  и ролях. Ловим сверкой каждого вызова `client.ts` с фактическими маршрутами.
3. **Целостность данных.** Между БД нет внешних ключей, операции неатомарны. Ловим
  SQL-проверками после каждого деструктивного сценария: поиск "сирот", проверка каскадов.

Поверх них обязательны негативное тестирование (пустые и пробельные значения, спецсимволы, битый JSON,
превышение лимитов, `status` вне справочника), проверка обработки ошибок (внутренние строки БД и английские
технические сообщения не должны попадать в русский интерфейс) и отдельный чек-лист доступности.

**Приоритеты (MoSCoW).** Must have - авторизация, ролевые права, создание и модерация наблюдения, файлы,
персистентность. Should have - проекты и задания, фильтры и поиск, участие, комментарии. Could have -
адаптивность, состояния загрузки, доступность. Won't have в этой итерации - нагрузка, кроссбраузерность, i18n.

## 5. Критерии входа и выхода

**Вход** - стенд развёрнут и `/health` отвечает `200`; миграции применены и соответствуют [sql/sql-
queries.sql](../sql/sql-queries.sql); seed загружен; есть задание с обязательным фото.

**Выход** - выполнены все проверки скоупа (Must + Should); каждое расхождение оформлено баг-репортом с Severity
и Priority; нет открытых Critical; нет открытых Major в ролевой модели и персистентности; актуальны отчёт и
матрица трассируемости.

## 6. Тестирование более ранних этапов

Так как основной метод - анализ кода, отдельно отмечены техники с наибольшим выходом дефектов: **сверка границ
валидации** между соседними обработчиками одного ресурса (находило асимметрию "поле проверяется при создании, но
не при обновлении"); **обзор схемы БД** на целостность (внешние ключи, каскады без подтверждения пользователя,
индексы на колонках выборок); **матрица прав доступа по коду** - ячейка "проверка есть в одном обработчике и нет
в соседнем" самый продуктивный способ найти дыру в авторизации.

## 7. Риски и ограничения

Все пять рисков **реализовались**, по каждому указано, что сделано.

- **Стенд недоступен** - результаты нельзя подтвердить на рантайме. Сделано: анализ кода стал
  основным методом, автотесты запускаются одной командой.
- **Нет нагрузочного стенда** - не оценена производительность при росте данных. Сделано:
  проверено отсутствие пагинации и лишних сканов на колонках без индексов.
- **Мало браузеров** - пропущены специфичные для движков дефекты. Сделано: фокус на семантике
  HTML и CSS, а не на визуальных различиях.
- **Чужой код как объект** - риск прочитать намерение автора как дефект. Сделано: находка
  формулируется как "наблюдаемое поведение", спорные - как вопросы к команде.
- **Дефекты нельзя исправить** - отчёт остаётся документом, а не историей фиксов. Сделано:
  приоритизация по влиянию и рекомендации, а не только факты.

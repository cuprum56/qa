# Методология тестирования

**Как** получены результаты: какие техники применялись и почему. Читать нужно до баг-репортов - иначе непонятно,
почему в "фактическом результате" нет скриншотов.

## 1. Объект и его устройство

"Общее дело" - микросервисное веб-приложение: почти каждая функция проходит через несколько слоёв.

```
Браузер (Next.js 16, React 19)
        |  HTTP + JSON, Authorization: Bearer <JWT>
        v
   Gateway :8080        <- единственная точка входа, токен, CORS, роутинг
   +--- user-service        :8081 -> users_db        (PostgreSQL 16)
   +--- project-service     :8082 -> projects_db     (PostgreSQL 16)
   `--- observation-service :8083 -> observations_db (PostgreSQL 16)
                            Redis 7 - сессии, MinIO - байты файлов
```

Следствия, использованные как гипотезы дефектов:

- **Три изолированные БД без внешних ключей** - искать "сиротские" записи через SQL после удаления.
- **Токен проверяется и в gateway, и в каждом сервисе** - при ошибке поведение может отличаться.
- **`GET /api/projects/**` публичен одним префиксным правилом** - анонимный доступ искать по всему дереву, а не
  только к карточке.
- **Публичные `download_url` выдаются в ответе** - недоступное "извне" может стать доступным по ссылке.
- **Multipart и JSON на одном эндпоинте создания** - сравнивать коды и тела ответов.

## 2. Применённые техники

**Статический анализ - основной метод находок.** Code review с фокусом на дефекты:

1. **Разбор путей данных:** где значение приходит, нормализуется, валидируется и попадает в БД. Пример: `title`
  наблюдения проверяется на пустоту при создании (`backend/observation-service/src/handlers/observations.rs:128`), но не при обновлении (`:297`).
2. **Границы доверия:** чему система верит безусловно - HTTP-статус соседнего сервиса, `Content-Type` файла от
  клиента, роль из токена вместо БД.
3. **Сверка контрактов:** каждый вызов `frontend/lib/api/client.ts` против маршрутов бэкенда - метод, путь,
  набор и обязательность полей, типы ответов.
4. **Инварианты схемы:** `VARCHAR`, `NOT NULL`, `UNIQUE`, `CHECK`, `ON DELETE CASCADE` - сравнение с тем, что
  реально проверяет приложение.
5. **Матрица прав "эндпоинт x роль":** ячейки, где проверка есть в одном обработчике и отсутствует в соседнем.

**Проектирование тест-кейсов.** Классы эквивалентности; граничные значения (пароли 5/6/72/73 символа, `title`
255/256, загрузка 2 МБ ровно и 2 МБ + 1 байт); таблицы решений "роль x действие x чужой ресурс"; переходы
`pending -> approved/rejected`; негативные сценарии - неверный, чужой и просроченный токен, чужая сущность,
отсутствующие поля, обход клиентской валидации.

**Анализ контракта API:** коды ответа для успеха, валидации, прав и отсутствия ресурса, единообразие тела ошибки
и заголовков, соответствие `Content-Type` содержимому. **Доступность** вынесена в отдельный чек-лист по WCAG 2.2
AA: самописные контролы без библиотек автоматикой не ловятся.

## 3. Шкалы оценки дефектов

Severity (вред) и Priority (срочность) - **разные шкалы**, в отчётах разделены явно.

- **Critical** - атака извне, утечка персональных данных, обход авторизации: API-01, API-02, API-15.
- **Major** - не работает в обычном сценарии, потеря или дублирование данных: WEB-01, API-08, API-09.
- **Minor** - работает с деградацией: неудобно, неочевидно, разная терминология: WEB-08, API-14.
- **Blocker** и **Trivial** не встречаются: опечатки поднимались до Minor, полная неработоспособность - до
  Critical.

Priority: **High** - в релизе или блокирует пользователей, исправить немедленно; **Medium** - до релиза или в
ближайшем спринте; **Low** - в бэклог, использование не блокируется.

Оценки ставились так: security-дефекты - **Critical по Severity** независимо от внедрения, оценка идёт по
ущербу, а не по вероятности эксплуатации; дефекты контракта между слоями поднимались на ступень.

## 4. Статусы тест-кейсов

- `Passed` - ожидаемый результат подтверждён анализом кода, расхождений нет.
- `Failed` - фактическое поведение расходится с ожиданием, расхождение подтверждено кодом.
- `Blocked` - проверку невозможно завершить из-за дефекта, указанного в поле **Кейсы**.
- `Not executed` - нужен стенд, автотест подготовлен, но не запускался.

## 5. Верификация и доказательная база

Стенд поднимается одной командой (`stand/README.md`): docker compose, seed и четыре учётные записи -
`scientist`, `volunteer`, `admin` и посторонний `stranger`.

Сценарии, фиксирующие известный дефект, помечены префиксом `[KNOWN BUG]` и проверяют **текущее ошибочное
поведение**: на непочиненном коде проходят, после исправления падают. Так дефект остаётся воспроизводимым, а
починка сразу видна. Разбор - в [docs/traceability.md](traceability.md#2-семантика-префикса-known-bug).

Каждый дефект содержит блок **Доказательство** вида `путь/к/файлу.rs:строка`: его можно перепроверить без
стенда. Ссылки - на состояние кода 03.06.2026.

## 6. Границы исследования

Что **не** проверено, чтобы не создавать ложного впечатления полноты:

- **HTTP-ответы рантайма** - нет доступа к Docker. Закрывается прогоном стенда и Newman.
- **Safari, Firefox и реальные устройства** - нет стенда, только эмуляция в DevTools.
- **Частичные отказы инфраструктуры** (Redis или MinIO лежат) - остановкой контейнера.
- **Платёжные и почтовые интеграции, мобичное приложение** - в объекте отсутствуют.

Производительность оценивалась **только по проектированию запросов** (нет пагинации, есть сканы и N+1 в клиенте)
- это вывод из кода, а не измерение.

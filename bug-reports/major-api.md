# Баг-репорты - Major, API

Дефекты уровня Major на стороне сервисов, заведены 04.06.2026. Индекс и метаданные - в [README.md](README.md).

Поле **Фактически** - поведение, выведенное из кода, а не наблюдённое на стенде: стенд не разворачивался (см. [README.md](README.md)).

### API-03. Невалидный токен возвращает `500` вместо `401`
**Severity:** Major | **Priority:** High | **Область:** все четыре сервиса | **Кейсы:** TC-API-06, TC-API-07
**Шаги.** Взять рабочий токен и испортить подпись (`alg: none` или чужой ключ), затем `GET :8080/api/users/me` с заголовком `Authorization: Bearer <испорченный>` - приходит `500` вместо `401`.
**Дефект:** отклонение токена отображается как внутренняя ошибка - в `status_code()` каждого сервиса вариант
ошибки JWT приравнен к `Internal`, поэтому `401` недостижим; проверка подписи при этом корректна - токены с
чужим ключом и с алгоритмом `none` отвергаются. **Ожидается:** `401` + `WWW-Authenticate`. **Фактически:**
`500` с текстом внутренней ошибки библиотеки. **Влияние:** пользователь с истёкшей сессией видит "HTTP error
500" вместо предложения войти снова, клиент ветвит логику по коду, в теле утекают детали крипто-библиотеки.
**Фикс:** отдать `401` для ошибок JWT в `status_code()`: `backend/gateway/src/errors.rs:45`
(`Self::Jwt`), `backend/project-service/src/errors.rs:59`, `backend/observation-service/src/errors.rs:66`,
`backend/user-service/src/errors.rs:67` (`Self::JwtEncode` - тот же тип `jsonwebtoken::errors::Error`,
назван по кодированию, а используется и при декодировании).

### API-04. Нет ограничения частоты запросов на вход
**Severity:** Major | **Priority:** High | **Область:** gateway, user-service, автоматизации нет
**Шаги.** `POST :8080/api/auth/login` со 100+ неверными паролями подряд, затем столько же `POST /api/users` с новыми email - ни одного `429`, ни счётчика, ни нарастающей задержки.
**Дефект:** ни шлюз, ни сервис не ограничивают частоту попыток входа и регистрации. **Ожидается:** `429` с
`Retry-After`, счётчик неудачных попыток на учётную запись и на источник. **Фактически:** все запросы
обрабатываются, а каждая неудачная попытка сверяет намеренно медленный `bcrypt` и сама занимает процессор.
**Влияние:** перебор паролей по словарю; отказ в обслуживании легитимных пользователей; создание учётных
записей для засорения данных. **Фикс:** лимит по IP и по учётной записи на шлюзе, экспоненциальная задержка,
уведомление о множественных неудачах; одинаковый ответ для существующего и несуществующего email.

### API-05. Роль фиксируется в токене и не сверяется с базой до 24 часов
**Severity:** Major | **Priority:** High | **Область:** user-service, автоматизации нет
**Шаги.** Войти под `admin`, затем понизить роль этой учётной записи в `users_db` до `volunteer`; со старым токеном вызвать `POST :8080/api/projects` - операция проходит.
**Дефект:** роль читается из токена, сверки с базой нет, функций отзыва сессий и обновления токена тоже нет.
**Ожидается:** `403`. **Фактически:** операция проходит до истечения срока токена (по умолчанию 24 часа).
**Влияние:** понижение прав не действует на активные сессии - скомпрометированная учётная запись администратора
остаётся функциональной. **Фикс:** хранить в Redis номер версии прав и сверять его со значением в токене на
каждом запросе либо проверять роль по базе; реализовать отзыв всех сессий, в том числе при смене пароля.

### API-06. Нет валидации формата email и длин текстовых полей
**Severity:** Major | **Priority:** High | **Область:** все сервисы | **Кейсы:** TC-API-04, TC-API-05
**Шаги.** `POST /api/users` с `{"email":"not-an-email","password":"Passw0rd","first_name":"X"}` - `201`; затем тот же запрос с `status` длиной 300 символов - `500` с текстом БД про `character varying(255)`.
**Дефект:** две независимые проблемы. *Формат email:* проверки нет - только `trim()` и нижний регистр
(`backend/user-service/src/handlers/users.rs:113`), поэтому принимаются `not-an-email`, пустая строка, `a@b`. *Длины полей:* ограничения есть
только в схеме БД (`title`/`email` - `VARCHAR(255)`, `phone`/`status` - `VARCHAR(64)`), приложение их не
проверяет. **Ожидается:** `400` с указанием поля и допустимого формата. **Фактически:** для неверного email -
`201`, запись сохраняется, и такой пользователь уже не сможет войти (формат отвергает браузер), а восстановить
доступ нельзя: писем в проекте нет; для длинных полей - `500` с `{"error":"error returned from database: value
too long for type character varying(255)"}`. **Влияние:** в базу попадают записи, с которыми невозможно работать;
пользователю показывается текст ошибки БД, а клиент по `500` считает запрос неисправимым. **Фикс:** валидировать
формат и длину на границе приложения, отдавать `400` с именем поля.

### API-07. Неопределённая семантика записи данных
**Severity:** Major | **Priority:** Medium | **Область:** project-service, observation-service | **Кейсы:** TC-API-11
**Шаги.** `POST /api/projects` с `"status":"banana"` и пустым `title` - `201`; `PUT` без `title` очищает заголовок; `PUT /api/observations/{o}` с полным списком полей от постороннего - `200` без проверки прав (срабатывает только при переданном списке изменяемых полей, `backend/observation-service/src/handlers/observations.rs:272-282`).
**Дефект:** четыре проблемы с общей первопричиной - нет контракта допустимых значений. 1. `status` хранится как
`VARCHAR` без справочника: принимаются `banana` и пустая строка, хотя интерфейс предлагает четыре значения.
2. Пустые заголовки принимаются при создании проекта и задания, хотя для наблюдений проверка есть - асимметрия
обработчиков. 3. При обновлении заголовок можно очистить; то же с текстом комментария. 4. `PUT` обрабатывается
тем же обработчиком, что `PATCH`: клиент "прочитал-изменил-записал" получает `200` и молча теряет данные; пустой
`PATCH` от постороннего тоже даёт `200`, хотя изменение полей ему запрещено - проверка прав срабатывает только
если передан изменяемый список (`backend/observation-service/src/handlers/observations.rs:272-282`). **Фактически:** `"status":"banana"` и пустой `title` сохраняются с `201`; `PUT` очищает заголовок; `PUT` и пустой `PATCH` от постороннего дают `200`; `status` без справочника отображается как пустое поле.
**Ожидается:** единый контракт - статусы по
справочнику, непустые заголовки при создании и обновлении, безусловная проверка прав, `PUT` != `PATCH`.
**Влияние:** проекты и задания без названия не идентифицируются в списках; отчёты без текста; статусы, которые
интерфейс не умеет отображать; утрата данных при `PUT`. **Фикс:** перечисления статусов (тип в Rust, `CHECK` в
схеме) с валидацией на входе; проверка непустого заголовка; развести `PUT` и `PATCH` либо убрать `PUT`;
сделать проверку прав безусловной.

### API-08. Фильтрация по тегам: клиент вызывает несуществующий метод
**Severity:** Major | **Priority:** High | **Область:** project-service, frontend | **Кейсы:** TC-API-13
**Шаги.** В каталоге выбрать тег из захардкоженного списка - фильтр применяется в браузере, проект с тегом "Гидрология" не находится; `GET :8080/api/projects/by_tags?tags=экология` - `200`, `POST` с тем же телом - `405`.
**Дефект:** интерфейс фильтрует по тегам в браузере, серверный метод не используется, а список из десяти тегов
задан в коде и не связан с реальными. **Ожидается:** единый контракт клиента и сервера - выбор тега фильтрует
серверную выдачу. **Фактически:** `GET /api/projects/by_tags?tags=экология,птицы` - `200`, `POST` с
`{"tags":"экология"}` - `405`; фильтр применяется к уже загруженным данным, поэтому проект с тегом "Гидрология"
не найдётся, а "Субтропический климат" совпадёт с "Климат" по подстрочному сравнению. **Влияние:** фильтр в
каталоге не работает, а несовпадение подписей выглядит как ошибка поиска. **Фикс:** перевести клиент на
серверный метод, убрать захардкоженный список, искать по точному совпадению тега.

### API-09. Пустой комментарий принимается, удаление уничтожает ответы
**Severity:** Major | **Priority:** Medium | **Область:** observation-service, автотеста нет
**Шаги.** `POST /api/observations/{o}/comments` с `{"comment":" "}` - `201`; `PUT` с тем же телом стирает текст существующего комментария; `DELETE` родительского комментария с ответом - `204`, строки `C2` и `C3` исчезают из базы.
**Дефект:** две проблемы. *Пустой комментарий.* Текст очищается от пробелов, но проверка на пустоту не выполняется
ни при создании, ни при обновлении (`backend/observation-service/src/handlers/comments.rs:133`): `{"comment":" "}` создаёт запись, а существующий
комментарий стирается полностью. *Каскадное удаление.* Ссылка на родительский комментарий с каскадным
удалением: удаление родителя молча удаляет всё дерево ответов. **Ожидается:** ответы не удаляются;
пользователь получает предупреждение либо текст помечается удалённым. **Фактически:** `204`, записи `C2` и
`C3` удалены из базы без подтверждения; восстановить нельзя - столбца `updated_at` нет. **Влияние:** пустые
записи и необратимая потеря переписки, а обсуждение наблюдения - основной способ согласовать детали со
счётчиком. **Фикс:** отклонять пустой текст и запрещать его очистку; заменить каскад "мягким" (`is_deleted` /
`deleted_at`) с заглушкой в тексте; ограничить глубину вложенности; добавить `updated_at`.

### API-11. Вступление в несуществующий проект завершается успехом
**Severity:** Major | **Priority:** Medium | **Область:** user-service, автотеста нет
**Шаги.** Взять произвольный UUID, `POST :8080/api/participations` с этим `project_id` - `201`; `GET /api/participations/{uuid}` отдаёт состав участников несуществующего проекта; после удаления проекта запись участия остаётся в базе.
**Дефект:** обработчик вступления выполняет только вставку - ни проверки существования проекта, ни обращения к
`project-service`; внешнего ключа нет, так как проекты хранятся в другой базе. **Ожидается:** `404`.
**Фактически:** `201`, запись создана; `GET /api/participations/{uuid}` отдаёт состав участников несуществующего
проекта, а после удаления проекта участие остаётся в базе и его удаление возвращает `204` - принадлежность к
удалённому проекту формально существует (проверяется запросами из
[sql-queries.sql](../sql/sql-queries.sql)). **Влияние:** мусорные записи, неотличимые от настоящих, и сообщение об
успехе при входе по прямой ссылке на отсутствующий проект. **Фикс:** проверять существование проекта вызовом
`project-service` до вставки - так же, как `observation-service` проверяет принадлежность задания проекту.

### API-13. Тип загружаемого файла определяется по заголовку клиента
**Severity:** Major | **Priority:** Medium | **Область:** observation-service | **Кейсы:** TC-API-14
**Шаги.** `POST /api/observations/{o}/files` multipart с исполняемым `.sh`, но у части `Content-Type: image/png` - файл сохранён, ссылка работает; тот же запрос без заголовка у части - `400` на корректном файле.
**Дефект:** тип берётся из `Content-Type` multipart-части, а не из содержимого. **Ожидается:** тип
определяется по содержимому, недопустимый тип отклоняется с `400`. **Фактически:** запрос принимается, файл
сохраняется и получает действующую подписанную ссылку; обратный случай тоже дефект - без `Content-Type` тип по
умолчанию `application/octet-stream`, которого нет в белом списке, поэтому корректный файл отвергается с
`400`. **Влияние:** хранилище исполняемых файлов, раздаваемых подписанными ссылками, при этом валидные файлы
отвергаются по недосмотру. **Фикс:** определять тип по сигнатуре содержимого; без заголовка определять по
расширению, а не отвергать; при несовпадении заголовка и содержимого - `400`.

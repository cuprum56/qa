# API-автотесты: Postman + Newman

Автоматизация проверок из [checklists/](../checklists/) и [test-cases/](../test-cases/).

## Состав каталога

- `postman_collection.json` - коллекция v2.1, 94 запроса в 10 папках, 386 assert-проверок.
- `environment.json` - URL, идентификаторы, токены. `newman.sh` - прогон в CI и локально,
  отчёты CLI, JSON, JUnit и HTML. `gen_tokens.py` - подпись JWT: истёкший, чужой, без `exp`.
  `validate_collection.py` - схема v2.1 и синтаксис, `summarize.py` - отчёты, `fixtures/` - multipart.

## Запуск

```bash
./stand/up.sh                          # 1. поднять стенд
./api/newman.sh                        # 2. прогнать всё
./api/newman.sh --folder "04 Projects"    # отдельная папка
./api/newman.sh --bail                   # стоп на первом падении
python3 api/validate_collection.py       # статика без стенда
```

Отчёты: `test-report/newman/report-<время>.{json,xml,html}`. Раннер проверяет `/health`, берёт `JWT_SECRET`
из окружения или `backend/.env`, подставляет абсолютные пути к фикстурам и компилирует JS через `node --check`.

## Структура коллекции

- `01 Auth` - 15: регистрация, вход, границы пароля (5/6/72/73), дубликат и регистр email, роль. API-06, API-15.
- `02 Authorization` - 12: матрица прав четырёх ролей против чужих ресурсов. API-02, API-07, API-15.
- `03 Users` - 5: профиль, частичное обновление, публичное представление. API-10, API-12.
- `04 Projects` - 18: CRUD, фильтры `title`/`tag`/`by_tags`, границы полей, `PUT`. API-06...API-08, API-14.
- `05 Missions` - 4: принадлежность миссии проекту по пути. Дефектов нет.
- `06 Observations` - 9: создание, модерация, статусы, чужой ресурс. API-07.
- `07 Files` - 7: multipart, белый список MIME, права, нет поля `file`. API-13.
- `08 Comments` - 7: вложенность, права удаления, каскад ответов. API-09.
- `09 Participations` - 6: вступление, повторное вступление, выход, чужая запись. API-11.
- `10 Contract` - 11: обработка токена, формат ошибок, `Content-Type`, лимит тела, 404/405. API-03, API-12.

Итого: **94 запроса**, **386 проверок**, из них **31 сценарий-дефект**.

## Соглашения

**`[KNOWN BUG]` (31 запрос).** Такой запрос фиксирует дефект: он проходит, когда ошибочное поведение
воспроизводится, и падает, когда дефект исправлен. Неудобно как "зелёный" критерий, но удобно как
триггер регрессии. Соответствие запросов и дефектов -
[docs/traceability.md](../docs/traceability.md#2-семантика-префикса-known-bug).

**`ДОКАЗАТЕЛЬСТВО`.** Проверки, подтверждающие дефект, названы явно, и в тексте сказано, **что именно
она доказывает**: `pm.test('ДОКАЗАТЕЛЬСТВО: в публичном профиле есть phone', ...)` проверяет наличие
`phone`. Отчёт читается как обоснование, а не как список красных строк.

**Защита от "каскада".** Тело каждого скрипта обёрнуто в IIFE с проверкой ответа: если запрос не дошёл
до сервера, вместо `JSONError in test-script` добавляется одна проверка `Ответ получен (нет сетевой ошибки)`.

**Порядок папок значим.** Переменные создаются в `01 Auth` (вход за волонтёра, учёного, администратора и
второго волонтёра); `04 Projects` создаёт и удаляет проект в конце папки, так как он нужен `05`-`09`.
Перезапуск без сброса БД накапливает данные: `run_id` идёт в email, но `Join project` ждёт `409` и вернёт `201`.

**Время ответа.** На каждый запрос - проверка "< 5000 мс" (уровень коллекции) и жёсткие локальные:
1000 мс каталог проектов, 500 мс профиль, 2000 мс регистрация (bcrypt).

## Чтение отчёта

`summarize.py` делит провалы на три категории, которые Newman показывает одним числом:

- **регрессии** - провалы в обычных сценариях: новый дефект или сломанная проверка.
- **дефект исправлен** - провал в `[KNOWN BUG]`: код починили, сценарий переводится в позитив.
- **сетевые ошибки** - запросы не дошли до стенда; прогон недействителен целиком.

Ожидаемый результат: **все проверки зелёные**, регрессий `0`, все `31` `[KNOWN BUG]` проходит. Коды
выхода: `0` ожидаемо, `1` регрессии, `2` стенд недоступен, `3` дефект перестал воспроизводиться.

## Данные стенда и фикстуры

Коллекция рассчитана на seed из [stand/](../stand/README.md). Пароль всех - `Passw0rd` (валидатор требует
6...72 байта, `backend/user-service/src/handlers/users.rs:83,88`). Роли: `volunteer` - владение наблюдением,
`stranger` - права, `scientist` - проекты и модерация, `admin` - верхний уровень прав. `project_id`,
`mission_id`, `observation_id` берутся из ответов папок `04`-`06`.

Фикстуры: `duck.png` - реальное изображение 64x64 (позитив); `not-really.png` - shell-скрипт с
расширением `.png`, передаётся как `image/png` и подтверждает API-13 (сервер доверяет заголовку
multipart и не проверяет сигнатуру); `payload.txt` - `text/plain` вне белого списка MIME, ожидается `400`.

## Открытые вопросы

Требуют живого стенда; в среде, где готовилось портфолио, Docker был недоступен.

1. **Усечение bcrypt.** Валидатор ограничивает пароль 72 байтами, но длину проверяет только при
   регистрации: вход с хвостом дал бы обход аутентификации (класс CVE-2019-20352), серьёзнее API-03.
2. **Гонка каскада.** `08 Comments` фиксирует исчезновение ответа с родителем; проверить `ON DELETE CASCADE`.
3. **Предел тела.** Задан трижды по 20 МиБ (`nginx.conf:10`, `backend/gateway/src/main.rs:21`,
   `backend/observation-service/src/main.rs:22`); потоковость чтения не проверена.
4. **`by_tags` при пустом `tags`.** Коллекция ждёт `200 []`; поведение стоит зафиксировать в контракте.
5. **`429`.** Сценариев лимита нет, пока не исправлен API-04; потом добавить проверку `Retry-After`.

## Как расширять

1. Новая проверка -> новый `pm.test` в существующем запросе; новая функция -> новая папка в конце.
2. Новый дефект -> запрос с `[KNOWN BUG]`, `ДОКАЗАТЕЛЬСТВО` в тексте и строка в баг-репорте с тем же ID.
3. После правки кода -> прогнать, убедиться, что упал **ровно один** сценарий, заменить ожидание, снять префикс.

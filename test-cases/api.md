### TC-API-01 - Регистрация и успешный вход
**Статус:** Passed | **Запрос:** `01 Auth / Register (volunteer)` | **Предусловие:** email свободен
**Шаги:** `POST /api/users` (volunteer) -> `POST /api/auth/login` -> `GET /api/users/me` с Bearer.
**Ожидается:** `201`; `200` + `token`; `200` + профиль; одна строка в `users_db.users`.
**Фактически:** соответствует, пароль хешируется `bcrypt`. Токен регистрация не возвращает, поэтому клиент обязан выполнить дополнительный вход (`backend/user-service/src/handlers/users.rs:79-146`) - это не дефект, но ломает ожидание "зарегистрировался - значит авторизован".

### TC-API-02 - Регистрация с уже существующим email
**Статус:** Passed | **Запрос:** `01 Auth / Register. Duplicate email -> 409` | **Предусловие:** email из TC-API-01 занят
**Шаги:** `POST /api/users` с тем же email и другим паролем; повторить с `" APIcase01@Example.COM "`.
**Ожидается:** оба запроса дают `409`; число записей в `users_db.users` не растёт.
**Фактически:** соответствует. Email нормализуется приведением к нижнему регистру с обрезкой пробелов (`backend/user-service/src/handlers/users.rs:113`), уникальность обеспечена уникальным индексом, нарушение отображается как конфликт, а не как внутренняя ошибка.

### TC-API-03 - Граничные значения длины пароля
**Статус:** Passed | **Запросы:** `Short password (5) -> 400`, `Too long password (73) -> 400` | **Предусловие:** стенд поднят
**Шаги:** `POST /api/users` четыре раза с паролями длиной `5`, `6`, `72`, `73` символа.
**Ожидается:** `5` -> `400`; `6` -> `201`; `72` -> `201`; `73` -> `400`.
**Фактически:** соответствует, границы выбраны верно, сервис проверяет обе (`backend/user-service/src/handlers/users.rs:83-91`). Верхняя граница 72 символа - ограничение `bcrypt`, решение корректное. Сообщение об ошибке приходит по-английски, учтено как WEB-09.

### TC-API-04 - Регистрация с некорректным форматом email
**Статус:** Failed -> [API-06](../bug-reports/major-api.md#api-06-нет-валидации-формата-email-и-длин-текстовых-полей) | **Предусловие:** стенд поднят
**Шаги:** `POST /api/users` со значениями `not-an-email`, `""`, `a@b`, `нет@почта`, `user@`, пробелы внутри адреса.
**Ожидается:** `400` для всех некорректных значений.
**Фактически:** значения сохраняются, ответ `201`. Обработчик делает только обрезку пробелов и нижний регистр (`backend/user-service/src/handlers/users.rs:113`). В системе появляются записи, по которым невозможно ни войти, ни восстановить доступ, так как отправки писем нет. Ограничение длины 255 символов тоже не проверяется.

### TC-API-05 - Переполнение текстового поля
**Статус:** Failed -> [API-06](../bug-reports/major-api.md#api-06-нет-валидации-формата-email-и-длин-текстовых-полей) | **Предусловие:** зарегистрирован учёный
**Шаги:** `POST /api/projects` с `title` длиной 256 символов; `PATCH /api/users/me` с `phone` длиной 65; `POST /api/projects` с `status` длиной 65.
**Ожидается:** `400` с понятным сообщением о превышении длины.
**Фактически:** `500` и тело `{"error":"error returned from database: value too long for type character varying(255)"}`. Ограничение есть только на уровне схемы БД (`VARCHAR(255)`), приложение его не проверяет. В интерфейс попадает текст внутренней ошибки БД, а по HTTP-коду клиент не понимает, что запрос нужно исправить.

### TC-API-06 - Подделанный JWT
**Статус:** Failed -> [API-03](../bug-reports/major-api.md#api-03-невалидный-токен-возвращает-500-вместо-401) | **Предусловие:** стенд поднят
**Шаги:** `GET /api/users/me` с `Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.подделка.подделка`; токен, подписанный чужим секретом; алгоритм `none`.
**Ожидается:** `401` во всех случаях, тело `{"error":"..."}` о недействительном токене.
**Фактически:** `500` с текстом ошибки криптографической библиотеки: `Jwt` в карте ошибок шлюза сопоставлен с `500` (`backend/gateway/src/errors.rs:44-46`). Алгоритм `none` и чужой ключ **отвергаются** корректно - уязвимости подписи нет; проблема в коде ответа и в утечке внутреннего текста.

### TC-API-07 - Просроченный токен
**Статус:** Failed -> [API-03](../bug-reports/major-api.md#api-03-невалидный-токен-возвращает-500-вместо-401) | **Предусловие:** срок действия токена истёк
**Шаги:** `GET /api/users/me` и `POST /api/auth/logout` с просроченным токеном.
**Ожидается:** `401` в обоих случаях; клиент понимает, что требуется повторный вход.
**Фактически:** `500` в обоих случаях - та же причина, что в TC-API-06. Клиент не может отличить "сессия истекла" от "сервер упал" и не предложит войти заново. Дополнительно не выставляется заголовок `WWW-Authenticate`.

### TC-API-08 - Анонимный доступ к дереву `/api/projects/**`
**Статус:** Failed -> [API-02](../bug-reports/critical.md#api-02-анонимный-доступ-к-персональным-данным-и-файлам) | **Предусловие:** UUID проекта, задания, наблюдения известны
**Шаги:** без `Authorization`: `GET .../missions`, `.../observations`, `.../observations/{obs}/comments`, `.../observations/{obs}/files`, `GET /api/participations/{project_id}`.
**Ожидается:** `401` для недоступного анонимно: переписки под наблюдением и персональных данных участников.
**Фактически:** все пять запросов дают `200` с данными. Правило публичности построено на префиксе, поэтому анонимным становится всё дерево (`backend/gateway/src/main.rs:177-184`). В комментариях видны `user_id` и тексты, в метаданных файлов - `object_key` и рабочий `download_url`, в участниках - `user_id`, имя, роль. Достаточно знать один UUID: он возвращается в публичном каталоге проектов.

### TC-API-09 - Создание проекта пользователем-волонтёром
**Статус:** Passed | **Запрос:** `02 Authorization / Create project as volunteer -> 403` | **Предусловие:** токен с ролью `volunteer`
**Шаги:** `POST /api/projects` с корректным телом; затем `GET /api/projects` - убедиться, что проект не создан.
**Ожидается:** `403`; проект не создаётся.
**Фактически:** соответствует, проверка роли выполняется на сервере до обращения к базе (`backend/project-service/src/handlers/projects.rs:162-170`). Кейс включён сознательно: важно показать, что серверная граница работает, и WEB-07 - это отсутствие отражения границы в интерфейсе, а не её отсутствие.

### TC-API-10 - Чтение чужого профиля раскрывает контакты
**Статус:** Failed -> [API-10](../bug-reports/minor-api.md#api-10-чтение-чужого-профиля-раскрывает-email-и-телефон) | **Предусловие:** зарегистрированы два пользователя, у одного заполнены телефон и email
**Шаги:** `GET /api/users/{id_другого_пользователя}`; повторить без токена через шлюз и напрямую.
**Ожидается:** только публичные поля: идентификатор, имя, роль, описание. Email и телефон - контакты, доступные самому пользователю и организатору.
**Фактически:** в ответе присутствуют `email` и `phone`. Обработчик называется `public_profile`, но возвращает полную структуру профиля (`backend/user-service/src/handlers/users.rs:55-64`, `:240`). Через шлюз запрос требует авторизации, но любой зарегистрированный пользователь получает контакты любого другого, включая администратора; `/api/users/{id}/projects` дополнительно раскрывает список проектов конкретного человека.

### TC-API-11 - `PUT` выполняет частичное обновление
**Статус:** Failed -> [API-07](../bug-reports/major-api.md#api-07-неопределённая-семантика-записи-данных) | **Предусловие:** учёным создан проект с описанием и тегами
**Шаги:** `PUT /api/projects/{id}` с телом, содержащим **только** `title`; получить проект и сравнить `description` и `tags` с исходными.
**Ожидается:** `PUT` заменяет ресурс целиком: либо все поля обязательны, либо метод отвергается с `405`.
**Фактически:** `200`, обновлено только `title`, остальные поля сохранены - `PUT` и `PATCH` обрабатываются одним обработчиком (`backend/project-service/src/main.rs:71-72`). Клиент, реализующий чтение-изменение-запись, получит `200` и потеряет данные, не заметив. Тот же приём в `user-service` и `observation-service`.

### TC-API-12 - Метасимволы в фильтре поиска
**Статус:** Failed -> [API-14](../bug-reports/minor-api.md#api-14-метасимволы-like-не-экранируются-в-фильтре-поиска) | **Предусловие:** в каталоге не менее трёх проектов
**Шаги:** `GET /api/projects?title=<буква>`; `?title=_`; `?title=%`; `?title=100%25`.
**Ожидается:** `_` и `%` ищутся буквально; `title=%` не возвращает все проекты.
**Фактически:** `_` и `%` обрабатываются как метасимволы `LIKE`, поэтому `title=_` и `title=%` возвращают весь каталог. Ввод подставляется в шаблон поиска без экранирования (`backend/project-service/src/handlers/projects.rs:62-65`), при этом известный символ экранирования не применяется. Для пользователя это выглядит как сломанный поиск, а в перспективе - как обход фильтров, построенных на этом параметре.

### TC-API-13 - Фильтрация по тегам: клиент и сервер расходятся
**Статус:** Failed -> [API-08](../bug-reports/major-api.md#api-08-фильтрация-по-тегам-клиент-вызывает-несуществующий-метод) | **Предусловие:** есть проекты с разными тегами
**Шаги:** `GET /api/projects/by_tags?tags=экология,птицы` - так эндпоинт зарегистрирован на сервере; `POST /api/projects/by_tags` с тегом в теле - так обращается клиент (`frontend/lib/api/client.ts:166-173`); выбрать тег в интерфейсе.
**Ожидается:** единый контракт клиента и сервера; выбор тега фильтрует серверную выдачу.
**Фактически:** `GET` даёт `200`, `POST` - `405`, поскольку на сервере зарегистрирован только `GET` (`backend/project-service/src/main.rs:69`). Метод `getProjectsByTags` **вообще не вызывается ни из одного компонента**: фильтрация выполняется в браузере по заранее заданному списку из десяти тегов. Тег "Климат" не найдётся, если его нет в захардкоженном списке, а "Субтропический климат" совпадёт с "Климат" из-за подстрочного поиска.

### TC-API-14 - Загрузка файла с подделанным MIME-типом
**Статус:** Failed -> [API-13](../bug-reports/major-api.md#api-13-тип-загружаемого-файла-определяется-по-заголовку-клиента) | **Предусловие:** пользователь - владелец проекта, задания и наблюдения
**Шаги:** загрузить корректный PNG через multipart -> `201`; загрузить исполняемый файл или HTML, указав в части `Content-Type: image/png`; проверить лимит размера.
**Ожидается:** тип определяется по содержимому, а не по утверждению клиента; недопустимый тип отклоняется с `400`.
**Фактически:** проверка построена исключительно на заголовке клиента (`backend/observation-service/src/handlers/files.rs:29-32`, `:96-98`), содержимое не анализируется. Файл с произвольными байтами принимается, сохраняется и получает действующую подписанную ссылку - это напрямую связано с API-01, где подписанные ссылки раздаёт анонимное дерево эндпоинтов. Обратный случай: если multipart-часть не содержит `Content-Type`, файл отвергается, хотя отсутствие заголовка не означает недопустимый тип.

### TC-API-15 - Публичная регистрация выдаёт роль учёного
**Статус:** Failed -> [API-15](../bug-reports/critical.md#api-15-публичная-регистрация-позволяет-выбрать-роль-учёного), Critical | **Предусловие:** email свободен, клиент без токена
**Шаги:** `POST /api/users` с `role: "scientist"` -> `POST /api/auth/login` -> `POST /api/projects` с полученным токеном -> расшифровать payload токена и сверить `role`.
**Ожидается:** `400` либо `201` с `role: "volunteer"`; значение `role` из тела игнорируется; проект на шаге 3 недоступен.
**Фактически:** `201 Created`, в ответе `role: "scientist"` (`backend/user-service/src/handlers/users.rs:94-102` - белый список ролей проверяется, источник значения нет). Вход проходит, в payload `"role":"scientist"`, шаг 3 даёт `201`: `can_manage_projects()` истинно (`backend/project-service/src/middleware/auth.rs:32-34`), поэтому проверка `backend/project-service/src/handlers/projects.rs:167` проходит. Подтверждения статуса учёного в модели нет.

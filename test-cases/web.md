### TC-UI-01 - Регистрация нового пользователя-волонтёра
**Статус:** Passed | **Запрос:** `01 Auth / Register (volunteer)` | **Предусловие:** `/auth/register` открыт
**Шаги:** роль "Волонтёр" -> имя, фамилия -> email -> пароль -> "Зарегистрироваться".
**Ожидается:** учётная запись создана, пользователь аутентифицирован; в `localStorage` появились `auth_token`, `user_role=volunteer`, `user_first_name`, `user_last_name`; переход в `/dashboard/volunteer`; в `users_db` роль `volunteer`, пароль - хеш.
**Фактически:** соответствует. Регистрация возвращает `201` без токена, клиент компенсирует повторным входом и сохраняет ключи (`frontend/app/auth/register/page.tsx:44-51`).

### TC-UI-02 - Регистрация с несовпадающим подтверждением пароля
**Статус:** Failed -> [WEB-02](../bug-reports/major-web.md#web-02-подтверждение-пароля-не-проверяется-при-регистрации) | **Предусловие:** email свободен
**Шаги:** имя, фамилия, email -> пароль `Passw0rd` -> подтверждение `Passw0rdX` -> "Зарегистрироваться".
**Ожидается:** регистрация не выполняется, под полем подтверждения - сообщение о несовпадении, аккаунт не создан.
**Фактически:** **регистрация проходит успешно.** Поле `confirmPassword` собрано в форме, но при отправке не читается - обработчик формирует запрос только из `firstName`, `lastName`, `email`, `password` (`register/page.tsx:27-39`). `required` выполняется, потому что поле заполнено, а совпадение значений не проверяется вовсе.

### TC-UI-03 - Регистрация с паролем короче 6 символов
**Статус:** Failed -> [WEB-03](../bug-reports/minor-web.md#web-03-подсказка-о-минимальной-длине-пароля-расходится-с-поведением) | **Предусловие:** email свободен
**Шаги:** фамилия, email -> пароль `12345` и такое же подтверждение -> "Зарегистрироваться".
**Ожидается:** пароль отклоняется на клиенте с понятным сообщением до обращения к серверу.
**Фактически:** клиент отправляет запрос, сервер отвечает `400` с текстом "Password must contain at least 6 characters", и этот **английский технический текст выводится в русском интерфейсе**. Подсказка "Минимум 6 символов" при этом показана заранее, а атрибута `minLength` в приложении нет ни разу.

### TC-UI-06 - Создание проекта учёным
**Статус:** Passed | **Запрос:** `04 Projects / Create project (scientist)` | **Предусловие:** учётная запись с ролью `scientist`
**Шаги:** страница создания -> название -> описание -> теги `экология, птицы, город` -> "Создать проект".
**Ожидается:** проект создан со статусом `active`, теги сохранены как отдельные записи, пользователь перенаправлен в кабинет, проект доступен в списке и в `projects_db`.
**Фактически:** соответствует. Статус устанавливается фиксированным значением `active` - выбрать другой при создании нельзя, это ограничение, а не дефект. Теги нормализуются: пробелы обрезаются, повторы в разном регистре схлопываются (`backend/project-service/src/handlers/projects.rs:389-405`).

### TC-UI-07 - Доступ волонтёра в кабинет учёного
**Статус:** Failed -> [WEB-07](../bug-reports/major-web.md#web-07-кабинеты-и-формы-защищены-только-на-клиенте) | **Предусловие:** пользователь с ролью `volunteer`
**Шаги:** ввести в адресной строке `/dashboard/scientist` -> вкладка "Проекты" -> `/projects/create`.
**Ожидается:** перенаправление в кабинет волонтёра либо сообщение об отказе; создание проекта недоступно.
**Фактически:** доступ к `/dashboard/scientist` открывается. Перенаправление срабатывает только при точном `user_role === 'volunteer'` (`dashboard/scientist/page.tsx:47-52`); при любом другом значении, включая подделанное в `localStorage`, кабинет отрисовывается целиком. Форма создания проверяет роль по той же недоверенной величине (`projects/create/page.tsx:26-37`), но данные страницы уже загружены под ролью учёного. Существенно, что **серверная** проверка работает: попытка создать проект с токеном волонтёра возвращает `403`. Защита есть, но только серверная.

### TC-UI-08 - Отправка отчёта с фотографиями
**Статус:** Passed | **Предусловие:** волонтёр присоединён к проекту, в задании включены требования "требуется фото" и "требуется место"
**Шаги:** название -> описание -> две фотографии -> место наблюдения -> "Отправить".
**Ожидается:** наблюдение создаётся, фотографии прикрепляются, показан экран "Наблюдение отправлено", статус `pending`, записи есть в `observations_db`, файлы - в `observation_files` и в MinIO.
**Фактически:** при штатной работе всех сервисов соответствует. Заметная особенность: клиент сжимает изображения через canvas в JPEG с понижением качества до 2 МБ, поэтому исходные EXIF-данные (время, координаты) теряются - для платформы гражданской науки это потенциально значимо (`tasks/[taskId]/page.tsx:15-58`).

### TC-UI-10 - Сбой загрузки фотографии при отправке отчёта
**Статус:** Failed -> [WEB-01](../bug-reports/major-web.md#web-01-сбой-загрузки-фотографии-приводит-к-дубликатам-отчётов) | **Предусловие:** условия TC-UI-08, хранилище файлов недоступно
**Шаги:** название, описание, место, одна фотография -> "Отправить" -> наблюдать ошибку -> "Отправить" повторно.
**Ожидается:** одна атомарная операция: либо наблюдение создаётся со всеми фотографиями, либо не создаётся ничего и повтор безопасен.
**Фактически:** операция состоит из двух независимых запросов: сначала создаётся наблюдение, затем в цикле грузятся фотографии (`tasks/[taskId]/page.tsx:131-138`). Если хранилище недоступно, фото не загрузится, но наблюдение **уже создано** - пользователь жмёт "Отправить" снова. Результат - два наблюдения с одинаковым содержимым, одно без фото. Идемпотентности нет.

### TC-UI-11 - Выход из аккаунта из бокового меню кабинета
**Статус:** Failed -> [WEB-05](../bug-reports/major-web.md#web-05-выход-из-аккаунта-не-очищает-персональные-данные) | **Предусловие:** пользователь аутентифицирован, ключи сессии записаны
**Шаги:** открыть `/dashboard/scientist` -> "Выйти" в боковом меню -> DevTools -> Application -> Local Storage; затем войти заново и повторить.
**Ожидается:** после выхода удалены все ключи сессии, включая роль и имя; повторный вход и выход работают одинаково.
**Фактически:** реализованы два разных выхода, и ведут они себя по-разному. *В шапке сайта* удаляются `auth_token`, `user_role` и `user_name` (`frontend/components/layout/Header.tsx:44-49`), но `user_name` не записывается ни одним сценарием - удаляется несуществующий ключ, а реальные `user_first_name` и `user_last_name` остаются. *В боковом меню* удаляется только `auth_token` (`dashboard/scientist/page.tsx:79-82`). На общем компьютере это утечка ФИО; сохранённый `user_role` влияет на перенаправление при следующем открытии кабинета.

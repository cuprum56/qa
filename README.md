## Как тестировалось

Основной метод - **статический анализ исходного кода и анализ контракта API**. Стенд не разворачивался: в этой WSL-дистрибутиве отключена интеграция с Docker Desktop, поэтому все статусы получены чтением кода, а не наблюдением за работающей системой.

Проверено без стенда: коллекция загружается в Newman, все 386 проверок **компилируются** (`api/validate_collection.py` проверяет каждый скрипт через `node --check`) - исполнения не было, поэтому в тест-кейсах написано "ожидаемый результат"; классификатор результатов протестирован на синтетических отчётах Newman (`api/test_summarize.py`, коды `0/1/2/3`); ожидаемые коды ответов выведены из кода обработчиков, а не из догадок (`403` на создании проекта волонтёром - `backend/project-service/src/handlers/projects.rs:167`, `201` при вступлении в несуществующий проект - `backend/user-service/src/handlers/participations.rs:55`); seed сверен со схемой из миграций (`stand/validate_seed.py`), все 26 SQL-операторов разбираются парсером `sqlglot` в диалекте postgres; числа в документах и взаимные ссылки между артефактами сверены автоматически перед сдачей.

Каждый дефект подтверждён **воспроизводимым кодом** со ссылкой вида `путь:строка` - все 63 такие
ссылки из отчётов проверены против репозитория объекта: файлы существуют, номера строк в диапазоне. Для трёх Critical приложены выдержки кода с
подсветкой строк дефекта ([screenshots/](screenshots/)). Проверки не ограничены интерфейсом: найдены SSRF, отсутствие авторизации на целом дереве эндпоинтов, рассинхрон контрактов фронтенда и бэкенда, отсутствие сброса PII при выходе. 31 из 94 запросов автотестов - исполняемые сценарии дефектов: они падают, когда дефект исправлен, и служат триггером регрессии.

```bash
./stand/up.sh backend                              # 1. поднять стенд (нужен Docker)
./api/newman.sh                                    # 2. прогнать 94 запроса, 386 проверок
./stand/up.sh psql users_db < sql/00-users-db.sql   # 3. сверить состояние трёх баз
# 4. сравнить фактический результат с ожидаемым и обновить тест-кейсы
```

Подробности - в [methodology.md](docs/methodology.md#5-верификация-и-доказательная-база).

## Ключевые находки

Найдено **28 дефектов**: 3 Critical, 15 Major, 10 Minor. Из них 18 связаны с безопасностью или блокируют основной сценарий работы.

- **API-15** - поле `role` приходит из тела `POST /api/users`, любой посетитель
  регистрируется учёным. `backend/user-service/src/handlers/users.rs:94-102`.
- **API-01** - `/api/file-proxy?url=` без аутентификации проксирует любой запрос от имени
  сервера (SSRF). `frontend/app/api/file-proxy/route.ts:28`.
- **API-02** - `GET /api/projects/**` помечен `public` и открывает без токена всё дерево,
  включая персональные данные и presigned-ссылки. `backend/gateway/src/main.rs:182`.
- **API-03** - подделанный или просроченный JWT даёт `500` вместо `401`.
  `backend/gateway/src/errors.rs:45`.
- **API-04** - нет ограничения частоты на `/api/auth/login`, перебор паролей не
  блокируется. Весь backend.
- **API-08** - фронтенд вызывает `POST .../by_tags`, бэкенд реализовал `GET`, поэтому
  фильтрация сломана и отдаётся `405`. `frontend/lib/api/client.ts:166`.
- **WEB-01** - неатомарная отправка отчёта: сбой загрузки фото оставляет созданное
  наблюдение, пользователь получает дубликат.
  `frontend/app/projects/[id]/tasks/[taskId]/page.tsx:131`.
- **WEB-07** - нет `middleware.ts`, волонтёру открывается `/dashboard/scientist`.
  `frontend/app/dashboard/scientist/page.tsx:47`.

Три Critical лежат в разных слоях и объединяются одной причиной: граница доверия нигде не проверяется на входе. Разбор - в [docs/metrics.md](docs/metrics.md).

## Объект тестирования

**"Общее дело"** - платформа, где учёный создаёт проект, формулирует задания, доброволец присоединяется и присылает наблюдения с фотографиями, учёный модерирует их. Ключевые сущности: `User` -> `Project` -> `Mission` -> `Observation` -> `Comment`, `File`, `Participation`. Роли: `volunteer`, `scientist`, `admin`.

Frontend - Next.js 16 (App Router), React 19, TypeScript 5, Tailwind CSS 4, русский UI
без i18n. Backend - Rust 2024, Actix Web 4, SQLx, Redis 7, MinIO (S3), JWT (HS256).

Архитектура - Gateway (`:8080`), за ним user-service (`:8081`), project-service (`:8082`)
и observation-service (`:8083`). Хранилища - три изолированные БД PostgreSQL 16
(`users_db`, `projects_db`, `observations_db`), Redis для сессий, MinIO для файлов.

Из-за того что базы изолированы, целостность данных не обеспечивается внешними ключами между сервисами - это отдельный класс дефектов, который проверяется отдельно в [sql/](sql/sql-queries.sql).
